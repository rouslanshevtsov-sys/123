# Правила фиксации причин исключения

Каждый проверенный и не подошедший кандидат попадает в полный аудит
(`stage_filter.json` → `excluded_audit` в competitor_set.json → лист Excel
«Проверены, но исключены») с **конкретной** причиной.

## Формат записи

```json
{"gid": 123456, "name": "Название сообщества", "reason": "<код>: <пояснение>"}
```

## Стандартные коды причин

| Код | Когда применяется |
|-----|-------------------|
| `own-group` | Это сообщество самого бизнеса |
| `closed-community` | Закрытое сообщество — контент недоступен проверке |
| `unavailable` | Нет данных groups.getById (удалено/заблокировано) |
| `low-audience` | Подписчиков меньше минимума из карточки (указать число) |
| `off-topic-name` | Название указывает на офтоп (барахолка, мемы, новости…) |
| `card-exclusion` | Срабатывает правило `exclude` из бизнес-карточки |
| `geography-mismatch` | География вне целевого региона карточки |
| `assortment-mismatch` | Ассортимент/аудитория не соответствуют include-критериям |
| `no-active-vk` | Есть только сайт без действующего сообщества VK (не является конкурентом по ТЗ) |
| `sales-model-mismatch` | Модель продаж/сегмент/формат несовместимы с карточкой |
| `api-error` | Кандидат не проверен из-за неустранимой ошибки API (сохранить код ошибки) |

## Требования

1. Причина конкретна и проверяема: с числами (`subscribers 320 < required 1000`)
   или цитатой правила карточки; запрещены «не подошёл», «прочее».
2. Одна запись = один кандидат; дубли по gid недопустимы.
3. Исключение фиксируется на том этапе, где оно произошло (фильтр, смысловая
   проверка, проверка источников).
4. Посты, исключённые из расчёта ER, документируются отдельно
   (`excluded_posts[].excluded_reason`, см. er-rules.md).
5. При недоборе конкурентов аудит исключений + поле `shortfall` в паспорте запуска
   образуют объяснение дефицита; критерии не ослабляются.
