# Контракт цепочки навыков (chain contract, v1.2)

Цепочка: **Интервью → Конкуренты → Лучшие посты → Анализ реакции рынка**.
Этот файл — единая точка правды по передаче данных между этапами. Все навыки
цепочки ссылаются на него; дублировать эти правила в SKILL.md запрещено.

## 1. Границы ответственности (один навык — один этап)

| Этап | Навык (реальное имя) | Читает | Пишет | НЕ делает |
|------|-------|--------|-------|-----------|
| 1. Интервью | `business-context-interview` | ответы пользователя, публичные источники | `business_context.json`, `business_card.md`, `provenance.json` | не ищет конкурентов, не анализирует посты |
| 2. Конкуренты | `search-vk-competitors` | только confirmed-контекст (+`provenance.json`) | `competitor_set.json`, `run_manifest.json`, Excel, промежуточные JSON | не редактирует контекст, не собирает посты для анализа лучших публикаций |
| 3. Лучшие посты | `analyze-vk-best-posts` | `competitor_set.json` (только список из файла) | `vk_posts_dataset.json`, `comments.json`/`comments_replies.json`, `competitors_vk_report.xlsx`, медиа | не ищет новых конкурентов, не строит выводов о рынке |
| 4. Реакция рынка | `vk-content-report` | `vk_posts_dataset.json` + `comments.json` + XLSX + `provenance.json` этапа 3 | `comment-signals.json`, `analysis-core.json`, `report.html` | не собирает новые данные, не даёт рекомендаций |

Правило: навык не «заглядывает» через этап — только через артефакты непосредственного входа.

## 2. Имена артефактов (канон, см. `scripts/common.py: ARTIFACT_NAMES`)

Реальные навыки пишут каждый в свою рабочую директорию (этап 2 — `output/competitor-analysis/`,
этапы 3–4 — `--workdir`); канон «одна директория запуска» (`Субагент 1/Запуск_YYYY-MM-DD/`)
рекомендуется для сквозного прогона. Имена ниже сверены с фактическими скриптами веток origin.

- `business_context.json` — полный машиночитаемый контекст (этап 1).
- `business_card.md` — человекочитаемая карточка (этап 1).
- `provenance.json` — компактный summary этапа 1 (~1 КБ): статус, даты, `contextHash`, счётчики, хэши файлов.
- Этап 2: **`competitor_set.json`** — основной файл передачи дальше (схема — `references/competitor-set-schema.md` навыка поиска; поля: `status`, `generated_at`, `business_context.{path,sha256,status}`, `time_window_hours`, `target_count`, `competitors[].{gid,name,screen_name,vk_url,site,members_count,competitor_type,avg_er,last_publication,…}`, `excluded_audit[]`, `provenance.run_manifest`); плюс `run_manifest.json`, Excel и промежуточные JSON (`pool_raw/stage_filter/qualified/posts_er`). Ранний черновик контракта называл файл `competitors.json` — это устаревшее имя (алиас в `LEGACY_ARTIFACT_ALIASES`).
- Этап 3: **`vk_posts_dataset.json`** (схема `vk_posts_dataset/v1`: `schema`, `run.*`, `communities[]`, `benchmarks`, `posts[].{post_id,url,er,benchmark,is_best,views_source,transcript_status,…}`, `clips_processing[]`, `unavailable[]`), **`comments.json`** (плоский вид `{post_id, comment_id, parent_id, from_id, text, likes}`; допустим массив без обёртки) и **`competitors_vk_report.xlsx`** (листы «Лучшие»/«Проверенные»). Устаревшие имена черновика: `best_posts.json`, `posts_summary.json`.
- Этап 4: `comment-signals.json`, `analysis-core.json`, `report-draft.json`, итог — **`report.html`** + машиночитаемые реакции (`market_reactions.json` — необязательный формат по выбору) и `provenance.json` входа этапа (создаётся `make_provenance.py` этапа 3 или вызывается на входе этапа 4).
- `chain_manifest.json` — итог цепочки (ведёт этап 4): хэши всех артефактов, происхождение, статусы проверок.

Компактные summary обязательны там, где их создаёт навык (этап 1 — `provenance.json`);
для этапов 2–3 роль summary выполняют первые страницы отчётов и поля `run`/`provenance`
входных файлов. Агент (LLM) при передаче читает компактные секции, а крупные списки
(`posts[]`, `excluded_audit[]`) — только точечно.

Совместимость форматов (выявлена перепроверкой по веткам):
1. `competitor_set.json` → этап 3: читает `competitors[].name/type/vk_url|group_id` —
   они есть в схеме этапа 2; плоский массив тоже принимается. Обратная связь: этап 2 пишет
   числовой положительный `gid`, этап 3 нормализует id к формату `-gid` — оба вида допустимы.
2. `type`: единый enum `direct | indirect | attention` во всех трёх схемах (проверять на входе).
3. Этап 3 → этап 4: `comments_replies.json` (ответы включены) должен быть сконвертирован в
   `comments.json` (плоский) — делает `build_outputs.py` этапа 3 или `make_provenance.py`;
   этап 4 не принимает вариант с вложенными `replies` без конвертации.
4. Хэш карточки: этап 2 фиксирует байтовый SHA-256 файла (fileSha256) — эталон происхождения;
   канонический хэш документа (`hashes.business_context.json`) используется внутри этапа 1
   и в summary (`contextHash`). Не смешивать два значения в одном поле.

## 3. Порог входа downstream-навыков

Функция `common.require_confirmed_context(path)` проверяет и блокирует запуск, если:
1. входной файл отсутствует → «сначала выполните навык интервью»;
2. JSON повреждён;
3. `status != "confirmed"`;
4. пустые обязательные поля (`REQUIRED_FIELDS`);
5. обнаружены секреты.

Downstream-навык обязан вызвать эту проверку до любого внешнего действия (поиск, API).

## 4. Происхождение и хэши

- Формат: `sha256:<64 hex>`. Канон JSON: `sort_keys=True, ensure_ascii=False, separators=(",",":")` (`common.canonical_hash`).
- Поле `hashes.business_context.json` внутри контекста — канонический хэш документа **без поля `hashes`** (иначе самоцитата). Проверяется так же (`final_validation.py`, проверка `hash_provenance`).
- В summary поле `contextHash` — тот же канонический хэш; позволяет обнаружить устаревший кэш.
- В `chain_manifest.json` для каждого файла два хэша: `canonicalHash` (для JSON-документов) и `fileSha256` (байтовый хэш файла).
- Любое изменение контекста после подтверждения требует пересчёта хэшей (`confirm_card.py` делает это автоматически) и инвалидирует summary последующих этапов (несовпадение `contextHash` → перезапуск этапа 2).

## 5. Передача файлов и кэш (расход токенов/контекста)

- Один скрипт читает каждый крупный файл **не более одного раза** за запуск.
- Повторное чтение исключено кэшем: `common.load_cached_summary(run_dir)` перечитывает
  `business_context.json` только если `provenance.json` отсутствует или его `contextHash`
  не совпал; иначе возвращает готовый summary (cache HIT).
- Агент (LLM) при передаче между этапами оперирует только summary-файлами; полные JSON
  открывает точечно (например, конкретный пост по id), а не целиком.

## 6. Безопасность токена и файлов

- Единое имя файла токена для всей цепочки: **`vk_token.txt`** в корне проекта
  (`common.TOKEN_FILE_NAME`). Переменная окружения: **`VK_API_TOKEN`**
  (общий fallback — `VK_TOKEN`, legacy-файл `.token` — поддерживается этапом 3,
  новым навыкам не добавлять). Файл обязан быть в `.gitignore` и никогда не коммитится.
- Токен не попадает ни в один артефакт цепочки; `detect_secrets.py --dir` сканирует всю директорию запуска и падает на любом секрете (сам `vk_token.txt` исключён из скана как легитимное хранилище). Ошибка сети логируется только с замаскированным токеном (`***REDACTED***`, см. `mask_token` этапа 2).
- Запрещены в файлах навыка и артефактах: данные текущего бизнеса, подписанные URL, абсолютные пути. Сканер путей не должен давать ложных срабатываний на собственных литералах правил: запрещённые префиксы собираются из частей (пример: `"/" + "workspace/"`), а не литералом целиком.
- Сетевые запросы к VK API выполняются только этапами 1–3 и только по публичным данным сообществ; запросы ограничены (`searchCriteria.count`, максимум поста на сообщество за проход).
- Артефакты не должны содержать выдуманных данных: пустое поле остаётся `null`/`[]` с явной меткой в MD («⚠️ Не заполнено»), правдивый `source.parseError` лучше отсутствующего.

## 7. Условия остановки (единые для цепочки)

Остановить этап и сообщить пользователю, если:
- пользователь явно отказался;
- входной артефакт не прошёл порог (§3) — останавливаемся до внешних действий;
- достигнут лимит попыток доступа к источнику (3 ошибки сети/API подряд);
- все проверки этапа пройдены и результат записан (нормальная остановка).

## 8. Версии схем и обратная совместимость

- `schemaVersion` контекста: `1.0` → `1.1` (добавлены необязательные `hashes`, `validation`, `generatedAt`) → `1.2` (контракт цепочки; имена артефактов зафиксированы здесь). Новые поля всегда необязательны; валидаторы принимают документы без них.
- `contractVersion` в summary — версия контракта передачи (`SUMMARY_CONTRACT_VERSION` в `common.py`).
- Совместимость JSON-схем: downstream-навыки полагаются только на поля, зафиксированные в §2 и в `SCHEMA` модуля `common.py`; собственные поля этапа не добавляются в чужие артефакты.
